# 2026-10-09 MYT — Real Windows Desktop 2 involuntary switch reproduced, source step identified

**Safety result: RED.** The owner previously confirmed four unwanted Windows virtual Desktop switches. This controlled A/B test found **one additional, instrumented Desktop1→Desktop2 transition**, and immediately halted at the first incident. Never erase or recategorize the owner's previous four reported interruptions.

## Experimental design

- Same user session, Windows Desktop1 owner / real virtual Desktop2 Agent target, same candidate native host and installed WinApp CLI v0.5.0. Existing production DeskMCP was not replaced/restarted.
- Both rounds created a **test-owned** WPF window on Desktop1, cloaked it, moved it with candidate native `move-window` to real Desktop2, and uncloaked it there. No global keyboard/mouse injection; no automatic desktop switch to Desktop2 or auto-return to Desktop1.
- Dedicated *passive* listener recorded foreground HWND and PID, desktop-change event notifications, 25ms polling fallback and a persistent stop tripwire. A Node harness recorded timestamps and bounded the child commands. Any first switch kills the in-flight command, ends the run and cleans up the test-owned processes.
- Run A (protected): current candidate WPF fixture, **WS_EX_NOACTIVATE on root and owned popup** before Show / uncloak.
- Run B (old/unprotected): verbatim fixture from `8979a91:test-area/desktop2-wpf-probe/Program.cs`, copied to isolated `legacy-wpf/` for comparison. It has `ShowActivated=false` + DWM cloak but **does not have WS_EX_NOACTIVATE or WPF owner binding**.
- Both trials used the same `trace-once.mjs` command sequence and observer instrumentation. The original GUI test script `test-area/d2-wpf-matrix.ps1` remained quarantined.

No native move/inspect step had produced a switch earlier in this run. The first switch occurred during the **WinApp CLI `ui set-value` execution window**, accompanied by the WPF target stealing the system foreground. **We identify the triggering action path, not the exact underlying Win32 SetForegroundWindow API caller.** The command was terminated before completion; do not claim its ValuePattern write completed.

**Important distinction:** The triggered command was a **direct test invocation of installed `winapp.exe ui set-value`**, not an invocation of DeskMCP's production `desktop_ui_action` MCP tool. The test is strong evidence against treating WinApp's `set-value` on arbitrary, unprotected real-Desktop2 WPF windows as inherently foreground-safe, but does **not** establish that the full production MCP action route was involved.

Microsoft's [WinApp CLI UIA documentation](https://learn.microsoft.com/zh-cn/windows/apps/dev-tools/winapp-cli/ui-automation) says `set-value` is an UIA/ValuePattern action that should not take foreground. The real observation demonstrates **an app/window/provider-dependent activation side effect** or other activation path during this command, not proof of which Win32 API call originated inside WinApp or WPF. The WPF fixture's `WS_EX_NOACTIVATE` change is the strongest difference explaining A/B, because popup Owner binding is not used until the final step (which this failing run never reached). Further API-level attribution would need instrumented WinApp/UIA provider activation tracing and must not be guessed.
